# Query Balatro 仕様書（SPEC）

作成日: 2026-11-16 / 更新日: 2026-11-16 / ステータス: **確定（MVP実装中）**

## 概要

Balatro系、クエリのパターンで役を作るスコアアタック。

ポーカー役の代わりにクエリのパターンで役を作る。断片カードを並べてクエリを組み、チップ×マルチでスコアを伸ばす。

## 面白さの核

**「断片を並べてクエリを組む」という行為そのものにリスクとリターンを持たせる。**

- リスク: 断片は5枚しか並べられない。強い役（JOIN・ウィンドウ関数）は強いが、断片の組み合わせを縛られる
- リターン: 役の倍率 × 返却行数。行を増やすほどチップは伸びるが、絞り込まないと役が上がらない
- 駆け引き: 「役を上げる」か「行を稼ぐ」かの二択を、残りプレイ回数と目標チップから逆算する
- Boss はデータではなくルールを縛る。使える断片が変わるので、同じ手札でも組み方が変わる

## 共通前提

- プレイヤーが書けるのは原則 `SELECT` のみ。DBは読み取り専用接続で開く
- 実行制限: 1クエリ 100ms / 取得上限 100行
- 1プレイ完結型。セーブはラン単位のみ
- オンライン対戦・ランキングはMVP外

### クエリ実行基盤の安全策（実装時に確定）

`node:sqlite` は同期APIのみで実行中断ができない。そのため「実行してから止める」ことができず、
**実行前に構造を検証してハングを防ぐ**方針を採る。実測（Node v26.13.0 / 本スキーマ）に基づく。

| 危険な形 | 実測 | 対策 |
|---|---|---|
| 4way クロス結合 | 48ms | — |
| 5way クロス結合 | 3,838ms | JOIN は最大3段に制限 |
| 6way クロス結合 | 120秒以上ハング | 同上 |
| 等値結合6段 + WINDOW + ORDER BY | 20,139ms | 同上 |
| 再帰CTE | 8秒 | 拒否 |

実行前検証の項目:

- `SELECT` 以外を拒否（`prepare().all()` は非SELECTでも実行してしまうため、実行前判定が必須）
- 複文を拒否（2文目以降が黙って無視され、「実行されたつもり」の事故になるため）
- 再帰CTE・`CROSS JOIN`・`ON` の無い JOIN・`ON 1=1`・`FROM a, b` 形式を拒否
- JOIN は最大3段

読み取り専用の担保:

- ファイルDBは `{ readOnly: true }` で開く
- インメモリDBは `:memory:` + `readOnly: true` では DDL を流せないため、
  スキーマ投入後に `PRAGMA query_only = ON` で読み取り専用に固定する

タイムアウトは実行後の経過時間で判定する（事後報告）。ハング防止は上記の構造検証が担う。

### 目標チップ（確定値）

| アンティ | Small | Big | Boss | Boss妨害 |
|---|---|---|---|---|
| 1 | 1,800 | 3,800 | 5,000 | なし |
| 2 | 3,600 | 5,100 | 6,800 | 重複でスコア0 |
| 3 | 5,000 | 8,200 | 10,000 | ORDER BY 禁止 |
| 4 | 7,400 | 10,800 | 13,000 | なし |
| 5 | 8,900 | 14,400 | 17,000 | LIKE 禁止 |
| 6 | 12,100 | 18,200 | 21,000 | なし |
| 7 | 16,300 | 19,000 | 22,000 | JOIN 禁止 |
| 8 | 22,000 | 22,500 | 23,000 | 取得上限50行 |

全段で単調増加。急に跳ねる段を作らない。

### 数値の決め方（実測ベース）

まず**理論上限**を実測した。全5ジョーカー所持時の1手の最大は **13,728**
（`chips 528 × mult 26`）。1ブラインドは4手なので上限は約 54,912。
目標はこれを超えない範囲に置く必要がある（超えると手札の運でしか突破できない）。

その上で貪欲AI（手札8枚から最大5枚の全218通りを毎手総当たり＋ディスカード活用＋
ジョーカー選択）で60ランを回し、勝率が **30%** になるよう逆算した。
このAIは**人間より強い**ため、人間の初見は10〜20%と推定される。

詳細と実測値は [BALANCE.md](BALANCE.md) を参照。

### 開始ジョーカー

`createRun()` は必ず「行の蒐集家」を1つ持った状態で始まる。

理由: ジョーカー0個→1個でスコアが約2.5倍になる。開始時0個だと、最初のジョーカーを
獲得した瞬間（アンティ1 Boss 突破後）に目標値が跳ね、**そこだけが壁**になる。
開始時から持たせることで曲線が滑らかになり、
かつ「ジョーカーでスコアが伸びる」という本作の核を最初の1手から体験できる。

### Boss 妨害の割り当て方針

`zeroOnDuplicate`（重複行でスコア0）は重複行を禁じるため使える断片が減り、
実測でもスコアが 10,017 で頭打ちになる。
これを終盤に置くと**その1点だけが突破不能の壁**になる。

そのため**制限の強い妨害は目標値の低い序盤に置き、終盤は「伸びを許す」妨害に留める**。
桜井原則の「一直線の坂にしない」に従い、Boss は目標値の跳ねではなく
句の制限で「攻略を考えさせる難所」にする。

## スコア式（確定）

```
チップ = 断片のチップ合計 + 返却行数 × 1 + ジョーカー由来チップ
マルチ = 役の倍率 + ジョーカー由来マルチ加算
スコア = Math.round(チップ × マルチ)
```

- 端数は最終スコアのみ四捨五入する（途中は切り捨てない）
- 上限は設けない（アンティ8 Boss の目標 23,000 が実質的な上限）
- 0行が返った場合は役なし・マルチ0・スコア0

## 役（確定）

優先度の高い順に評価し、最初に成立した役を採用する。

| 役 | 条件 | マルチ |
|---|---|---|
| ロイヤル相当 | JOIN + WINDOW + GROUP BY | ×10 |
| フルハウス相当 | WINDOW を含む | ×6 |
| ストレート相当 | JOIN を含む | ×4 |
| フラッシュ相当 | BETWEEN または IN を含む | ×3 |
| ツーペア相当 | LIKE を含む | ×2.5 |
| ペア相当 | WHERE を含む | ×2 |
| ハイカード相当 | 1行以上返った | ×1 |
| 役なし | 0行 | ×0 |

定義は `src/data/ranks.ts`。役の条件は `RankCondition`（allKinds / anyKinds / noneKinds / minRows）で宣言的に書く。

## 断片カード（確定）

句の種類は `SELECT_EXPR` / `JOIN` / `WHERE` / `GROUP_BY` / `HAVING` / `ORDER_BY` / `LIMIT`。
組み立てはプレイヤーが並べた順ではなく、**SQL の正規の句順**で行う（並び順の試行錯誤を要求しない）。

- 断片は1枚で意味が通る SQL 片として定義する
- タグ（`FragmentKind`）は句とは独立。1枚が複数タグを持てる（例: LIKE 断片は `clause=WHERE`, `kinds=[WHERE, LIKE]`）
- 役・Boss・ジョーカーの判定はすべてタグに対して行う

定義は `src/data/fragments.ts`。

## ジョーカー（確定）

| ジョーカー | 効果 |
|---|---|
| NULL の使者 | NULL を含む行があればマルチ +4（定額） |
| LIKE の釣り人 | LIKE を含む断片1枚につきチップ +30 |
| 行の蒐集家 | 返却行1行につきチップ +5（**開始時に所持**） |
| 窓の魔術師 | WINDOW を含む断片1枚につきマルチ +3 |
| 秩序の否定 | ORDER BY を使っていなければマルチ +5 |
| 重複の鏡 | 完全重複行があればマルチ +6（定額） |

定義は `src/data/jokers.ts`。効果は `JokerEffect` の判別可能ユニオンで宣言し、logic 側が評価する。

**行数に比例する効果は「チップ」側だけに限る。** マルチを行数に比例させると
58行 × 4 = +232 マルチになり、目標値を桁違いに超えてゲームが崩壊する（実測で確認）。
仕様書の「NULL行を含むクエリはマルチ+4」「重複行で+2」は**定額**として解釈する。

### ジョーカーの獲得

ブラインドを突破するたびに、候補3つから1つを選んで獲得できる（枠5まで）。
候補がある間はプレイできない（報酬を受け取らずに進めない）。
所持済みのジョーカーは候補に出ない。

## Bossの妨害（確定）

データ側ではなくルール側を縛る。

| Boss | 妨害 | 割り当て |
|---|---|---|
| 妨害なし | 通常 | アンティ1・4・6 |
| 重複でスコア0 | 完全重複行を含むクエリはスコア0 | アンティ2 |
| ORDER BY 禁止 | ORDER BY を含むクエリを実行できない | アンティ3 |
| LIKE 禁止 | LIKE を含むクエリを実行できない | アンティ5 |
| JOIN 禁止 | JOIN を含むクエリを実行できない | アンティ7 |
| 取得上限50行 | 取得上限が50行に下がる | アンティ8 |

定義は `src/data/bosses.ts`、アンティへの割り当ては `src/data/antes.ts`。

**制限の強い妨害は序盤に置く。** 理由は「数値仕様」の「Boss 妨害の割り当て方針」を参照。

## ゲーム用DBスキーマ（確定）

プレイヤーが FROM に置くベーステーブルは `cards` のみ。

| テーブル | 役割 |
|---|---|
| `cards`（ビュー） | ベーステーブル。`cards_raw` から `id` を落としたビュー |
| `cards_raw`（実体） | 52枚 + 重複6枚。`edition` / `seal` は NULL を含む |
| `suits` | JOIN の的。4行 |
| `ranks` | JOIN の的。13行 |

**`cards` をビューにして `id` を落としている理由**: `SELECT *` に主キーが混ざると、
どの2行も絶対に一致しなくなり、重複系ジョーカーと Boss「重複でスコア0」が永久に発動しない。
`id` を落とすことで完全重複行が実際に発生する（58行中12行が重複）。

- NULL 列を意図的に用意し、NULL 系ジョーカーと `IS NULL` 断片の意味を作る
- 重複行を意図的に用意し、重複系ジョーカーと Boss「重複でスコア0」の意味を作る

定義は `src/data/schema.ts`。

## 断片の組み立て規則（確定）

- プレイヤーが並べた順ではなく、**SQL の正規の句順**で組み立てる（並び順の試行錯誤を要求しない）
- `HAVING` 断片だけを置いた場合は `SELECT COUNT(*) AS n` に正規化する
  （`SELECT * ... HAVING` は SQLite が拒否するため、断片単体で使うと必ず失敗する。
  それでは「置いたのに何も起きない断片」になり、プレイヤーが理由を理解できない）
- `LIMIT` 断片を複数置いた場合は先頭の1つだけ採用する

## 勝敗条件（確定）

- 勝利: アンティ8のBossを突破
- 敗北: ブラインドの目標チップにプレイ回数内に届かない

## モジュール構成（確定）

```
src/
  types.ts        共有型契約（全モジュールが依存する唯一の型定義）
  data/           断片・役・ジョーカー・Boss・アンティ・DBスキーマ
  db/             読み取り専用クエリ実行基盤（QueryEngine）
  logic/          役判定・スコア計算・ラン進行（RunController）
  cli/            対話UI
tests/            node:test
scripts/          バランス検証
```

依存方向は `types ← data ← db ← logic ← cli`。逆方向の import を禁止する。

## エラーの扱い（確定）

プレイヤーに見せる失敗は2系統に分ける。同じ文言で出すと、プレイヤーが何を直せばいいか分からない。

| 系統 | 型 | 例 | UIの出し方 |
|---|---|---|---|
| 入力ミス | `PlayError` | 6枚選んだ / 手札にない / 回数が残っていない | 操作の直し方を伝える |
| クエリ失敗 | `PlayError` の `query-failed`（`cause` に `QueryError`） | SQLエラー / Boss妨害 / タイムアウト | クエリの何が悪いかを伝える |

SQLite の生の英語エラーはそのまま出さない（`HAVING clause on a non-aggregate query` 等）。
日本語に変換して表示する。
