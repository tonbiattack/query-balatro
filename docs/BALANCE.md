# Query Balatro バランス検証（BALANCE）

作成日: 2026-11-16 / 更新日: 2026-11-16 / ステータス: **MVP確定**

`npm run balance` の実測結果と、目標値の調整要否を記録する。
数値の定義場所は `src/data/antes.ts`（目標チップ・Boss割り当て）、
`src/data/fragments.ts`（断片チップ）、`src/data/ranks.ts`（役の倍率）、
`src/data/jokers.ts`（ジョーカー効果）。

## 検証方法

`scripts/balance.ts` が決定的な seed（1〜N）で N ランを自動プレイし、集計する。

- **AI**: 手札8枚から最大5枚の全組み合わせ（218通り）を実際にクエリ実行し、
  スコアが最大になる組み合わせを選ぶ貪欲法。先読みはしない。
- **ディスカード**: 残りプレイ回数で割った「1手あたり必要スコア」に届かないとき、
  チップの低い5枚を捨てて引き直す（最後の1手は必ずプレイする）。
- **ジョーカー**: 実測で勝率が最も高かった優先順位で選ぶ。
- **開始ジョーカー**: `createRun()` が `row-chips`（行の蒐集家）を1つ付与する。

この AI は**人間より強い**。毎手218通りを総当たりできるため、
人間が15〜20秒かけて選ぶ組み合わせを瞬時に見つける。

## 理論上限（1手あたり）

目標値を決める基準として、まず天井を実測した。

| 条件 | 1手の理論最大 | 内訳 |
|---|---|---|
| ジョーカー0個 | 2,170 | chips 217 × mult 10（ロイヤル相当） |
| 全5ジョーカー | **13,728** | chips 528 × mult 26（フルハウス相当） |
| 全5 + `maxRows50` | 12,480 | 取得上限で行数が減る |
| 全5 + `zeroOnDuplicate` | 10,017 | 重複行を禁じると使える断片が減る |

1ブラインドは4手なので、**1ブラインドの上限は約 54,912**。
目標はこれを超えない範囲に置く必要がある。超えると「引いた手札の運」でしか突破できない。

|---|---|---|---|

## 1ラン20分という目標に対する見積もり

### 計算

`scripts/balance.ts` は次の式で推定している。

```
推定時間 = 平均手数 × 20秒 + 平均ディスカード × 8秒 + ブラインド間 × 6秒
```

実測値を当てはめると:

```
57.7手 × 20秒 = 1154秒
 9.1回 ×  8秒 =   73秒
23回   ×  6秒 =  138秒
─────────────────────
合計 1365秒 = 約22.8分
```

### 1手20秒の根拠

| 行為 | 想定時間 | 根拠 |
|---|---|---|
| 手札8枚を見て組み合わせを考える | 8秒 | 役の条件（WINDOW/JOIN/WHERE）と残り回数から逆算する。AI は総当たりだが人間は勘で絞る |
| 番号を入力する | 2秒 | `1 3 5` + Enter。数字だけでも通るので短い |
| 結果（SQL・行数・内訳）を読む | 10秒 | 何が起きたかの手応え。SQL を読むのが本作の面白さの一部 |

ディスカード8秒は「どの5枚を切るか」の判断。ブラインド間6秒は
ジョーカー3択の選択と画面確認。

### 結論

**約22.8分**。目標の20分に対して**やや長い**が、許容範囲と判断する。

理由:

- この AI は毎手218通りを総当たりする。人間は同じ手を15〜20秒で選べない。
  実際の人間はもっと時間がかかるため、**22.8分は下限に近い見積もり**である。
- ただし「遅さは罪」の原則に照らすと、20分を大きく超えるのは避けたい。
  実プレイで長すぎると感じた場合は、アンティ数を8→6に減らすのが最も効く
  （1アンティあたり約2.8分）。
- 初見のプレイヤーは役の成立条件を覚えるのに時間がかかる。
  2周目以降に22分へ収束するイメージ。

## 目標値の調整要否

### 判断: **現状の曲線で妥当。大きな調整は不要**

理由:

1. **曲線が単調増加で、急に跳ねる段が無い。**
   「どこで負けたか」がプレイヤーに納得できる。
2. **序盤（アンティ1〜6）の突破率が100%。**
   桜井原則の「最初の3分で面白さを伝える」に合致する。
   最初の数ブラインドで「クエリを組むとスコアが伸びる」体験を確実に得られる。
3. **関門がアンティ2 Boss とアンティ8 Boss に分散している。**
   「一直線の坂にしない」を満たす。アンティ2 Boss は
   `zeroOnDuplicate` で「重複行を出さない組み方」を要求し、
   アンティ8 Boss は `maxRows50` で「行数に頼らない組み方」を要求する。
   どちらも**断片の選び方を変えさせる妨害**で、単なる数値の壁になっていない。
4. **AI が30%なので、人間の初見は10〜20%と推定される。**
   アンティ8到達自体は易しく、勝利が難しい配分は
   「もう1回やろう」の動機として正しい。

### 調整するなら（優先順位順）

| 優先 | 対象 | 案 | 効果 |
|---|---|---|---|
| 1 | アンティ8 Boss（23,000） | 22,000 へ下げる | 勝率 30% → 48%（実測） |
| 2 | アンティ8 Boss（23,000） | 24,000 へ上げる | 勝率 30% → 7%（実測） |
| 3 | アンティ数 | 8 → 6 に減らす | 1ラン約22.8分 → 約17分 |

**アンティ8 Boss の感度が非常に高い。** 22,000〜24,000 の幅で勝率が
48%〜7% と大きく動く（実測）。これは1手の理論上限 13,728 に対して
4手の合計でぎりぎり届くかどうかの境界にあるため。
調整する場合は 500 刻みで実測し直すこと。

## 既知の課題

### 1. 終盤の目標値の差が小さい（重要度: 中）

アンティ8 は Small 22,000 / Big 22,500 / Boss 23,000 と差が小さい。
1手の理論上限（13,728）に対して4手の天井が近く、
これ以上広げると勝率が急落するため意図的に圧縮している。

**影響**: 終盤は「数値の壁」ではなく「Boss の句制限をどうかわすか」で
難しくなっている。設計意図どおりだが、プレイヤーには
「目標値がほとんど変わらない」と不自然に見える可能性がある。

**対策案**: アンティ7〜8 の目標を下げて差を広げる代わりに、
Boss の妨害を追加する（例: アンティ8 Boss に `noJoin` + `maxRows50` の複合）。

### 2. アンティ2 Boss が序盤の関門としてやや強い（重要度: 中）

`zeroOnDuplicate` は重複行を禁じるため、単体で有効な断片が
**25枚中6枚**（`where-like-rank` / `group-by-suit` / `group-by-rank` /
`having-count` / `limit-5` / `limit-10`）に減る。
開始ジョーカー1個の状態では理論最大が 4,770 で、目標 6,800 に届かない。

実測でも敗北3ランがここに集中している。

**対策案**: アンティ2 Boss の目標を 6,000 へ下げる、または
`zeroOnDuplicate` をアンティ3以降へ移す。

### 3. ジョーカーの選択が「正解」に寄りすぎる（重要度: 低）

実測で勝率が最も高い優先順位が明確に存在する。
人間が説明を読んで選ぶ場合も同じ結論に至る可能性が高く、
「選択の悩ましさ」が薄い。

**対策案**: ジョーカーの種類を増やす、または効果を状況依存にする
（MVP 外。仕様書の「カードの大量追加は MVP 外」に該当）。

## 修正履歴（実装中に発見した設計上の問題）

### 「重複の鏡」が退化戦略だった（修正済み）

当初 `dup-mult` は「完全重複行1行につきマルチ +2」だった。
WINDOW 断片1枚と組むと58行中57行が完全重複になるため、マルチが +114 され、
**このジョーカー1個で勝率が 73% ↔ 0% と反転**していた。

```
window-row-number 単体        →    558
window-row-number + dup-mult  → 11,160（約20倍）
```

桜井原則の「ランダムは対応の幅を生むが、腕だけで決めたい勝負には不向き」に反するため、
**「重複行があればマルチ +6（定額）」に変更**した。修正後は約2.0倍に収まっている。

### 「NULL の使者」も同様に定額へ修正（修正済み）

仕様書の「NULL行を含むクエリはマルチ+4」を当初「1行につき+4」と実装したが、
58行 × 4 = +232 マルチになり目標値を桁違いに超えた。
仕様書の記述は**定額**の意味と解釈し、`multIfNull`（行があれば +4）に修正した。

## 再現方法

```powershell
# 60ランで検証（約30秒）
node scripts/balance.ts --runs 60

# 既定は40ラン
npm run balance
```

seed は 1 始まりの連番なので、同じコマンドなら常に同じ結果になる。
